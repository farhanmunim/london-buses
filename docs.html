1. What this is

London Buses is a website that lets you explore every bus route in London: search routes, see them on a map, check live arrivals and live bus positions, browse operators and garages, and dig into contract data — who runs each route, what it cost, and when it comes up for tender again.

It is an independent project, not affiliated with Transport for London. All the data comes from public sources.

2. The big idea

There is no server. The whole platform is one Git repository:

  • GitHub Actions is the scheduler and the computer. Workflows run on a timetable, fetch data from public sources, check it, and commit the results back to the repository.
  • Git is the database. Every dataset is a JSON file in the repo. History is free — every past state of the data is a commit.
  • Cloudflare Pages is the host. It serves the repository as a static site. The JSON files under data/api/ act as the site's "API" — the browser just fetches them like any other file. We call this the faux-API.
  • Live things stay live. Arrivals, live bus positions and service status are never stored — the browser fetches them directly from TfL, or through one tiny edge function (see section 9).

Why this design? It costs nothing to run, there is nothing to keep online or patch, and every data change is reviewable in Git history.

4. The frontend

The app is a single-page app written in plain JavaScript inside index.html. There is no bundler and no framework — you can read the whole thing top to bottom.

  • Routing: the URL hash decides the view — #/ routes list, #/route/25, #/map, #/stops, #/stop/<id>, #/operators, #/operator/<name>, #/garages, #/garage/<code>, #/vehicle/<reg>, #/tender, #/cpi, #/about. A hashchange listener calls navigate(), which renders the right view into <main>.
  • Data layer: a small D object wraps fetch() for each faux-API file and caches the promise, so each dataset is downloaded once per visit.
  • Safety around async: every navigation bumps a token (navToken); renderers re-check it after each await so a slow fetch from an old view can never overwrite the current one. All polling timers register in one list that is cleared on navigation, and the Leaflet map is destroyed on navigation too.
  • Maps: Leaflet with CARTO basemap tiles (light and dark variants). Route lines come from the overview GeoJSON; optional layers add stops, live buses, garages, low bridges and collision heatmaps.
  • Theming: CSS custom properties define a light and a dark palette; a tiny script sets data-theme before first paint from the stored choice or the system preference. color-scheme is declared per theme so native widgets follow.
  • Escaping: every remote string that lands in innerHTML goes through one esc() helper. CSV exports also guard against spreadsheet formula injection.

5. The data pipeline

npm run refresh runs scripts/refresh.js, which executes 17 steps in order. Steps 1–12 fetch; steps 13–16 build; step 17 is the quality gate. Fetch steps may fail softly (the last good data stays); build steps must succeed; a failed audit aborts everything so bad data is never committed.

#ScriptWhat it does
1fetch-data.jsDownloads TfL's route-geometry ZIP and writes one GeoJSON per route (both directions).
2fetch-route-destinations.jsTfL API → route names and destinations.
3fetch-route-stops.jsTfL API → the ordered stop list per route, plus one big stop directory.
4fetch-garages.jsGarage list (londonbusroutes.net) geocoded via postcodes.io, with OSM as fallback.
5fetch-frequencies.jsTfL timetables → is each route high- or low-frequency.
6fetch-route-details.jsScrapes operator, garage, PVR, vehicle type and contract dates per route (community reference site).
7fetch-vehicle-fleet.jsTfL's iBus registration list joined with DVLA lookups (make, fuel, age) — sticky 90-day cache so only new vehicles are queried.
8fetch-route-vehicles.jsSamples TfL live arrivals to see which actual vehicles worked each route today.
9fetch-tenders.jsEvery published TfL tender award since 2003. Awards never change, so only new IDs are fetched.
10fetch-tender-programme.jsParses TfL's annual tendering-programme PDFs → which routes come up for tender and when.
11fetch-line-status.jsSnapshot of service status and the diversion register (the live feed still wins in the browser).
12fetch-cpi.jsONS CPI index (series D7BT) and the contract-price-adjustment rates derived from it.
13build-classifications.jsJoins everything into one master record per route (type, deck, propulsion, operator, garage, PVR, fleet stats, contract history). Applies route-overrides.json last — manual fixes always win.
14build-overview.jsSimplifies all route geometry into one network-wide GeoJSON the map can draw at once.
15build-garage-locations.jsGarage coordinates in the shape the frontend wants.
16build-api.jsAssembles the faux-API: reshapes the primary datasets into data/api/*.json plus a manifest. Any field it cannot derive this run keeps its last good value.
17audit-data.jsData-quality gate: per-field plausibility checks on every record. Critical failures abort the run, so nothing broken is committed.

8. Refresh schedules

Four workflows share one concurrency group so runs never overlap. They only commit — and the site only redeploys — when the data actually changed. Cron times are UTC; the app's About page shows them in London time (GMT/BST).

WorkflowSchedule (UTC)Refreshes
weekly-refresh.ymldaily 03:17The full 17-step pipeline (name is historical).
refresh-status.ymlevery 2 h, 07:41–21:41Service status + diversion register.
refresh-fleet.yml07:20 / 15:20 / 23:20Arrivals sweep + DVLA fleet data.
refresh-tenders.ymlhourly 07:20–20:20, plus chained off every other runTender awards + programme.

GitHub's cron can slip a slot by minutes to hours, which is why the tender check also chains off the other workflows' completions (the workflow_run event fires reliably even when cron slots are dropped).

9. Live data

Three things are live and never stored:

  • Arrivals boards — the browser calls TfL's Unified API directly (it allows cross-origin requests without a key at browser rates). Boards count down every second and re-sync every ~30 s.
  • Route status — fetched from TfL on view and re-polled every 60 s, with the committed snapshot as fallback if the live call fails.
  • Live bus positions — the DfT BODS GPS feed needs a secret key and blocks cross-origin calls, so the browser calls /api/live/vehicles?line=25 instead. That's a ~90-line Cloudflare Pages Function which adds the key, filters the feed to the route's bounding box, and caches at the edge for 10 seconds so heavy use never hammers BODS.

All live surfaces are built to survive a flaky feed: last-good data stays on screen with a quiet "reconnecting…" note, and polling backs off and recovers on its own.

10. Keeping the data honest

  • Last-known-good everywhere. If a source is down, every builder falls back to the previous value. A flaky scrape never blanks a field.
  • Sticky caches. Immutable facts (DVLA records, tender awards) are cached and only new items are fetched.
  • Manual overrides. data/route-overrides.json pins hand-verified corrections that beat any scraped value — for example, route 660's vehicle type, which the upstream reference still lists wrongly.
  • Cross-checks. audit-vehicle-data.js compares our per-route vehicle verdicts against independent sources (bustimes.org, DVLA, TfL arrivals) and writes disagreement reports to data/audit/.
  • A hard quality gate. The final pipeline step checks every record for plausibility (types, ranges, referential joins). Critical problems abort the run before anything is committed.

11. Testing

The suites in tests/ run the real app in headless Chromium (Playwright) with every external feed mocked, so they pass offline and never depend on TfL being up. They cover mobile layout and overflow, the dark/light banner, tender tables and analysis, CPI maths against ONS reference values, hazard layers, live-feed resilience (outage → recovery), and the migration guarantees (no calls to retired hosts). Run one with node tests/verify-<name>.mjs.

12. Hosting and deploys

  • Cloudflare Pages builds from main: every push (code or data commit) becomes a deploy. There is no build step — Pages just serves the files.
  • _headers sets security headers and makes JS/CSS revalidate on every load (no fingerprinted filenames, so revalidation keeps returning browsers consistent after deploys).
  • _redirects keeps old URLs working (/v2 → /; the old changelog → the archive).
  • Budget: schedules are sized so data commits stay around ~12/day — comfortably inside Pages' 500 free builds/month with room for code pushes.

13. Rebuild it from scratch

The recipe, in order. Nothing here is magic — each step is ordinary Git, JSON and static hosting.

  1. Fork or clone the repository. It already contains working data, so the site runs immediately with no keys.
  2. Serve it locally: npm install, then any static file server (npx serve .) from the repo root. Open the served index.html — everything works from the committed JSON.
  3. Get keys (only needed to refresh data): a TfL Unified API key, a DVLA Vehicle Enquiry key, and a DfT BODS key. All free. Copy .env.example to .env and fill them in.
  4. Run the pipeline: npm run refresh. Watch the 17 steps; the audit at the end must pass. Individual steps can be run alone (see package.json scripts).
  5. Host it: create a Cloudflare Pages project pointed at your repo, production branch main, no build command, output directory /. Set BODS_API_KEY as a Pages environment variable so the live-vehicles function works.
  6. Schedule it: add the two API keys as GitHub Actions secrets (BUS_API_KEY, DVLA_API_KEY). The four workflows in .github/workflows/ then keep the data fresh automatically. Public repos get unlimited Actions minutes.
  7. Fix data by hand when needed: add an entry to data/route-overrides.json, run npm run build-classifications && npm run build-overview && npm run build-api, and commit. Overrides survive every future refresh.
  8. Verify: run the suites in tests/ (they need Playwright's Chromium; the tests download nothing and mock all feeds).
Building a similar project for another city? The shape transfers directly: find the transit agency's open API and any supplementary registers, write one fetch script per source with last-known-good fallbacks and a sticky cache for immutable facts, join everything into one record per route, serve the result as static JSON, and let scheduled CI commit changes. The frontend only ever reads flat JSON, so it doesn't care where the data came from.

14. Glossary

PVRPeak Vehicle Requirement — how many buses a route needs at the busiest time of day.
TVRTotal Vehicle Requirement — PVR plus spare buses (engineering cover).
DeckDouble-decker or single-decker.
PropulsionWhat powers the bus: diesel, hybrid, electric or hydrogen.
Tender / awardTfL contracts each route to an operator through competitive bidding; the published result is the award.
TrancheA numbered batch of routes tendered together.
£/mileThe award's cost per contracted live mile — the headline price of running the route.
CPI-CPAContract Price Adjustment: TfL contracts rise with 85% of CPI inflation, via a point-to-point or rolling-average formula.
iBusTfL's on-bus tracking system; its open data lists every vehicle's registration and operator.
BODSThe DfT Bus Open Data Service — the national live bus GPS feed.
Faux-APIThis project's term for committed JSON files served statically but consumed like an API.
